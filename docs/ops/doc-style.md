# 日本語文書の書き方

`README.md`・`CLAUDE.md`・`docs/` 配下・コミットメッセージ本文・PR 本文に当てる規範である。

## なぜリポジトリの中に置くか

文書の書き方は、書き手ではなくリポジトリの持ち物である。

規範を作業者の手元（各自のツール設定や個人の習慣）に置くと、書く人が替わった時点で文体が
変わる。**成果物にしか存在しない規則は、外から来た既定に負ける。** 既存のファイルを真似て
書けば揃うように見えるが、新しいリポジトリを立てたときや、全編を新規に書いたときには
真似る先が無い。

書いてあれば、誰が書いても、AI に書かせても同じものが出る。

## コミットメッセージと PR の言語

**本文は日本語で書く。** コミットメッセージの本文と PR 本文には、この規範をそのまま当てる。

件名（コミットの1行目）と PR タイトルは、英語でも日本語でもよい。このリポジトリの既存の
履歴に合わせる。どちらの言語でも命令形で書き、`feat:` のような type prefix は付けない。

**言語を揃えるためだけに、既に書いたものを書き換えない。**

## 文体

**である調で揃える。** 1つのリポジトリの中でですます調と混ぜない。読み手が複数いて、
文書が長く残ることを前提にしているためである。

体言止めを続けない。事実を述べる文は述語まで書く。

## 冗長を削る

- 同じ主張を言い換えて繰り返さない
- 場面や例を示した直後に、その内容を要約し直さない。意味づけの一文だけを置く
- 「重要なのは〜である」のような前置きで主張を予告しない。主張をそのまま書く
- 「この状況を解決するために」のような、次に書く内容を予告するだけの文を置かない
- 読者が自力で補える中間段階の説明を書かない
- 接続や評価のためだけの文（「それ自体はよいことである」など）を置かない

## 中身のない型を使わない

次の言い回しは、書いた側が具体を持たないまま埋めるときに出る。頻度と文脈で判断し、
出たら中身に置き換える。

- **予告と総括**: 「本文書では〜を扱う」「まとめると」「要するに」「〜に他ならない」
- **空虚な形容**: 「不可欠」「核心的」「鍵となる」「根本的な」「多角的」「包括的」
- **空虚な動詞**: 「掘り下げる」「深掘りする」「言語化する」
- **効能をぼかす「効く」**: 「〜に効く」「ここが効く」。何がどう良くなるのかを書く。
  規則の適用範囲を言う「常に効く」のような用法は残してよい
- **姿勢だけの宣言**: 「正面から扱う」。扱う内容そのものを書く
- **根拠のない緩和**: 「〜と言えるだろう」「〜かもしれない」。推量・仮定を表す場合は残す
- **予防線の積み上げ**: 「一概には言えないが」「あくまで一例だが」。言い切れないなら条件を書く
- **空虚な強調**: 「非常に」「極めて」「大いに」
- **無理な三点整理**: 「大きく分けて3つの」と先に数を決めてから列挙する型。論点の数だけ書く

## 翻訳調を避ける

日本語として成立していても、英語の構文が透けるものは避ける。

| 避ける | 直す |
|---|---|
| 〜することができる／〜することが可能です | 〜できる |
| 〜することによって | 〜すると／〜すれば |
| この事実は〜を示している | この事実から〜と分かる |
| 〜という観点から／〜という点で | 〜で見ると／〜については |
| 〜を持つ（抽象名詞が目的語） | 〜がある |

## 対象を名前で呼ぶ

- 「AI」「ツール」のような広い語でぼかさない。名前があるものは名前で呼ぶ
- 術語・固有名を導入したら、以後はその語で通す。曖昧語に後退しない
- 例示では、結果の羅列や受動態ではなく、行為者を主語にした動作で書く
- 架空の人物設定を冠しない

## 同じ型を繰り返さない

定義文の型、文の書き出し、文末の形のいずれも、3回続けたら入り口か構造を変える。

「〜ではなく、〜」の否定と肯定の対比は、読み手が実際に誤解しそうな場面に限る。見分け方は、
対比の後半だけで文が成立するかどうかである。

**段落あたりの分量を揃えない。** 重い節は厚く、軽い節は正直に軽く書く。全節が同じ厚みに
見える構成そのものが、機械が書いた合図になる。

## 演出の節度

- 太字を多用しない。誤読を防ぐ否定や、節の結論に限る
- 短い断定を独立した段落にする書き方は、その文書の山場に限る
- ダッシュ（`—`）を地の文で使わない。補足は括弧に、言い換えは読点か句点で処理する
- 慣用表現をひねった比喩、指す内容が一意に決まらない比喩を使わない

## 書かないもの

- **日付入りの履歴コメント。** 「2026-01時点で〜」のような時系列の記述を本文に残さない。
  経緯は git log とコミットメッセージが持つ
- **固有の接続情報。** ホスト名・IP・アカウント名・端末の資産番号を地の文に直書きしない。
  設定ファイルの実体は実値のまま動かす。この規範は地の文にだけ当たる
- **特定の実行環境に依存する事情。** 判断や手順の理由としてそのまま書かない。理由として
  要るなら一般の条件へ言い換える
- **外部の仕組みへの参照。** 下敷きにするのはよいが、参照先として書かず、切り出して
  このリポジトリに作り直す。他の担当者が同じ手順を踏めることが要件になる

## 既存の文書を直すとき

**既定は keep である。** 直すのは、その箇所を直すことで読み手の得を具体的に言える場合だけに
する。

個々の修正が正しくても、同じ変換を全箇所へ一律に当てると、その処理の均質さ自体が新しい
機械臭になる。元の文書が持つ不揃い（節ごとの濃淡、口語の引用、表記の癖）は欠陥ではなく、
実際に読解を妨げている箇所だけを整える。

主張と論旨は変えない。変えるのは表現だけである。元の文書が未解決のまま置いている論点に、
見解を書き足さない。本文の「未定」を断定に格上げしない。

意図的な表現か規範違反か区別できない箇所は、直さずに user へ報告する。

## 書き終えたら確かめる

- **見出しと各段落の先頭文だけを抜き出して読む。** 細部を読み直すより構成の乱れが見つかる
- **段落から固有名詞・数値・実例を抜いても文意が変わらないなら、一般論で止まっている。**
  原因は書き方ではなく素材の不足にあり、言い回しを直しても解決しない。素材を集め直すか、
  空欄として残す
