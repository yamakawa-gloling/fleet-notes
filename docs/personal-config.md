# 手元の Claude Code 環境と Fleet

手元の Claude Code を作り込んで使っている立場から、Fleet で試したこと、Fleet 側の仕組み、
使ってみて考えたことをまとめる。一人の利用者の感想として読んでほしい。

Fleet の仕組みについては、本家のコード（`4c616d3` 時点）とガイドを読んで確かめた。根拠の
ファイルを各所に書く。実機で試していないことは「未確認」と書き、読み違いがあれば直す。

## 試したこと

Fleet のワークスペースでリポジトリの Markdown を1ファイル直し、PR を出した。手元の CLI で
同じ作業をすると次の2つのフックが走るが、Fleet では走らなかった。

- Markdown を編集してターンを終えたとき：Stop フックが、変わった行を日本語の校正に回す
- `gh pr create` の直前：PreToolUse フックが、PR 本文を校正役の agent に通させる

一方、リポジトリの `.claude/` に置いたフック（ブランチの規約のガードなど）と skill は、
Fleet でも手元と同じように効いた。

走らなかった理由は、校正のフックを手元の `~/.claude/settings.json` に置いていたことにある。
Fleet の claude は、ワークスペース用の設定ディレクトリを読む（次の節）。置き場所の違いによる
もので、Fleet の動作としては自然である。

## 手元の環境で使っているもの

dotfiles のリポジトリを home-manager（Nix）で複数の端末に配り、`~/.claude` の中身を揃えている。

- グローバルの `CLAUDE.md`：応答の言語と一人称、地の文で接続情報を伏せる規則、コメントの書き方など
- フック：Markdown を編集した後の日本語の校正（`claude -p` を裏で起動する）、PR 本文の校正、
  特定のリポジトリへの本番操作のガード、メモリ書き込みのガード、構文チェック、
  SessionStart での応答方針の注入
- agent と skill：日本語の校正役、メモリの書き方、Issue の起票など
- メモリ：ホーム直下の1ディレクトリに、1つの事実を1ファイルで置く
- シェル：zsh の関数（作業ブランチと worktree を作ってセッションを起動する、レビューコメントを
  集めるなど）と、Nix で入れたツール
- MCP の接続、gh と git の認証

## Fleet 側の仕組み

- ワークスペースの claude は `CLAUDE_CONFIG_DIR=/var/lib/af/claude` を読む
  （`control-plane/internal/runtime/runtime_docker.go`）。このディレクトリはホームと別の
  マウントにあり、作り直しでもホーム掃除でも消えない（`workspace/notes/environment.md`）。
- 起動時に `--setting-sources` で読み込み元を絞っていないので、ユーザー層とプロジェクト層の
  settings は通常どおり読まれる（`workspace/agent/internal/agents/claude/program.go`）。
- Agent が `settings.json` にセッション状態のフックを足すときは、既存の配列に追記し、利用者の
  キーやフックを残すように作られている（同じディレクトリの `hooks.go`・`settings.go`）。

個人の設定ごとに、Fleet で対応するものは次のとおりである。

| 手元の設定 | Fleet での対応 |
|---|---|
| グローバルの `CLAUDE.md` | ⚙設定 →「エージェントへの指示」に書ける（8 KiB まで）。書き出し / 取り込みで別の環境へ移せる（本家ガイド `06-agents`・`12-settings`） |
| MCP | ⚙設定 →「MCP サーバー」で個人登録できる（`12-settings`） |
| メモリ | claude の自動メモリ（`projects/*/memory/`）がそのまま残る。Fleet 独自の AF メモリもある |
| フック | Console から登録する経路は見当たらなかった。`/var/lib/af/claude/settings.json` に書けば Agent の書き込みで消えないことはコードで確かめた。発火するかは未確認 |
| skill・agent | `/var/lib/af/claude/skills/`・`agents/` に置けば読まれるはずだが、未確認 |
| シェル環境 | bash・tmux・jq・python などが入っている。自分で入れるものは `~/.local` に置く（`workspace/Dockerfile`、`workspace/workspace-notes.md`） |
| リポジトリの `.claude/` | 手元の CLI と同じように読まれる |

個人の設定のうち、指示本文・MCP・メモリは Console から扱えるようになっている。

## 使ってみて感じたこと

手元の運用は、自分のワークフローに合わせて少しずつ組み上げてきたものである。Fleet は指示本文・
MCP・メモリ・リポジトリの `.claude/` まで柔軟に受け止められる作りで、利用者のフックを消さない
ように追記するなど、作り込んだ人への配慮もコードの随所にある。それでも私の場合は、フックや
skill、シェル環境まで手元に寄せすぎていて、Fleet で同じ流れを作るには整合を取り直す作業が
要りそうだと感じた。

もしかすると、似た人はほかにもいるかもしれない。並行稼働や複数のエージェントの使い分けに
関心を持つ人は、すでに自分の環境を作り込んでいることがある。そういう人は、移るときに
整合を取る手間を感じやすい。

## 自分の使い方

今進めている案件のリポジトリは、基本的に手元の環境で進める。そのうえで Fleet にも慣れて
おきたいので、小さな作業から少しずつ Fleet で試していく。これから始めるプロジェクトでは、
チームの開発基盤として Fleet を本格的に使いたいと考えている。

Fleet に期待しているのは、手元の環境では代えにくい次の点である。

- **チームで環境を揃える**：同じリポジトリを複数の人が編集するとき、ワークスペースのイメージと
  リポジトリの `.claude/` が共通なので、各自の手元の差に左右されにくい。手元の作り込みは
  自分にしか効かないが、Fleet ならチームの全員が同じ前提で作業できる。
- **同じ環境で動きを見る**：ワークスペースで立てたアプリを、ブラウザペインやプレビュー用
  サブドメインでその場で確かめられる。ポートを開ける手配も要らない（本家ガイド `10-integrations`）。
- **AI を使った開発を広げる基盤にする**：AI を使った開発に慣れていない開発者でも、Console から
  同じ手順で始められる。チームの規約やフックをリポジトリの `.claude/` に置けば、誰が起動しても
  同じように効く。

Fleet で作業するときは、次のように使い分けている。

- Fleet でも効かせたいフック（校正やガード）は、リポジトリの `.claude/` に置く。イメージに
  ある bash・jq・node・python だけで動くように書き直す。
- 応答の言語や口調などの指示は「エージェントへの指示」に写す。
- 手元のシェル関数や Nix で入れたツールに頼る作業は、手元の CLI で行う。

### Docker を前提にした構成をどう扱うか

今の案件のリポジトリは、ローカル開発を `docker compose` 前提で組んでいる。MySQL 8.4、S3 互換の
ストレージ（SeaweedFS）、帳票の PDF を作る Python のプロセスをコンテナで立てる。帳票のプロセスは、
組版をローカルと CI で揃えるために、WeasyPrint と日本語フォントをコンテナに閉じている。

Fleet のワークスペースには Docker が無い（`workspace/notes/environment.md`）ので、このままでは
同じ手順でプレビューできない。本家で確かめた範囲では、置き換えの候補は次のとおりである。

| compose のサービス | Fleet での候補 |
|---|---|
| MySQL 8.4 | `af-db up mysql` で同じ 8.4 が立ち、ポートも 3306 で揃う（`03-code`）。compose で渡している起動オプション（`--log-bin-trust-function-creators` など）は、別に合わせる必要がある（未確認） |
| S3 互換のストレージ | MiniStack を pip で入れれば、Docker 無しで S3 の API を試せる（`10-integrations`）。SeaweedFS の代わりに動くかは未確認 |
| 帳票のプロセス | 標準のイメージには、ブラウザペイン用に pango と Noto CJK フォントが入っている（`workspace/Dockerfile`）。Python の依存を `~/.local` に入れれば動く見込みだが、未確認。ただし、コンテナに閉じて組版を揃えるという今の方針とは別の経路になる |

どれも成り立ちそうだが、Fleet 用に別の起動手順を持つと、手元と Fleet で二通りの手順を保つことに
なる。今の案件を手元の環境で進める理由の一つはここにあり、どこまで寄せるかはまだ悩んでいる。
これから始めるプロジェクトでは、最初から Docker に頼らずに立ち上がる構成にしておけば、
この悩みは小さくできる。

## 見せ方について考えたこと

環境を作り込んだ人とは逆に、AI を使って開発しているが、並行稼働や複数のエージェントの
使い分けまではまだ試していない人には、Fleet の良さがまっすぐ伝わりそうだと思った。
「AI 駆動の開発には、まだこんなこともできる」と気づいてもらい、それを Fleet で試してもらう
という流れである。

LP が機能を一通り見せる入口になっているので、その先の見せ方として、機能を1つずつ使ってみて
ワークフローがどう変わるかを紹介する記事（ブログ）のようなものも考えられる。題材の例を
挙げておく。どれも本家のガイドに書かれている機能である。

- 並行稼働してみる：同種の修正を複数のセッションへ振り分けて同時に回す（本家ガイド `08-organising` のユースケース「型 2」）
- エージェントを使い分ける：同じ課題を Claude と Codex に当てて比べる（`06-agents` の早見表、`08-organising` のユースケース「型 3」）
- 指揮を任せる：フリート・オペレーターや定時実行で、セッションの起動と見張りを任せる（`08-organising`）
- 作業を受け渡す：handoff や子セッションで、長い作業を区切って引き継ぐ（`02-sessions`）
- 人に見せる：共有セッションで、作業の途中を同僚に見てもらう（`02-sessions`）
- その場で確かめる：動かした Web をブラウザペインで開き、エージェントと一緒に確認する（`10-integrations`）

試す前と後で、待ち時間や手戻りがどう変わったかが具体的に書かれていると、読む側は自分の
作業に重ねて想像しやすいと思う。

## 読んでいて気になった点

コードを読んでいて気になったことを、念のため残す。意図どおりの動作であれば問題ない。

### rtk の切り替えと、利用者の Bash フック

⚙設定で rtk をオン・オフすると、`settings.json` の `PreToolUse` のうち `matcher: "Bash"` の
要素がまとめて入れ替わるように読めた（`settings.go` の `ensurePreToolUseMatcher`・
`removePreToolUseMatcher`）。利用者が同じ matcher で自分のフックを書いている場合は、
それも一緒に外れるかもしれない。セッション状態のフックは追記で扱われているので、少し
気になった。

### 設定ディレクトリに手で置く使い方

フック・skill・agent を `/var/lib/af/claude` に置けば動きそうだが、メンバー向けガイドには
まだ記述が無い。`workspace/workspace-notes.md` にはエージェントが `~/.claude` などに触れない
ための決まりがあり、メンバーが手で置く使い方が想定に入っているのか、判断がつかなかった。
